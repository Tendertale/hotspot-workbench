# 热点信息管理二次开发：Agent 工作流与验收要求

## 目标与执行边界

在 `ticket-processing-auto-analysis-workbench` 基础上，将工单处理改造为“热点线索研判工作台”，交付可演示的完整流程：录入线索 → 查询与筛选 → DeepSeek 或本地规则分析 → 人工修改 → 确认应用 → 跟踪或归档 → 统计查看。

本文件采用现有仓库的 **Vue 3 + SQLite** 技术栈。根目录 `AGENTS.md` 已同步为本项目约束；架构与 API 契约见 `docs/architecture.md`。

本项目直接在用户自己的独立仓库中创建和提交，不 fork 原有仓库；交付工作流必须包含专门的 PR 创建、提交、review 反馈处理和证据核对责任人。

主 Agent 负责拆分任务、核对证据、判断完成状态和最终报告。实现、数据分析、独立代码审计以及测试均交由子智能体完成。各子智能体须明确文件所有权，避免并发修改同一文件；主 Agent 在集成后逐项验收。主 Agent 的模型与推理强度由 Codex 界面设置；目标配置为 GPT-6 Sol、High。

## 基线与技术约束

- 当前仓库前端是 Vue 3 组合式 API、Vite、Tailwind CSS 和 Lucide；后端是 Python 3.8+、FastAPI、Pydantic、httpx 和 SQLite。优先复用已有组件和分层，不引入与演示规模不相称的框架。
- 保留 OpenAI 兼容接口调用方式及默认模型配置 `deepseek-v4-flash`。DeepSeek 和本地规则是显式可选的两种模式；模型失败不得伪装成规则分析成功。
- 默认数据库路径为 `data/tickets.db`，`TICKET_DB_PATH` 可指定其他 SQLite 文件。空数据库首次启动时写入至少 8 条热点线索演示数据，不再写入工单样例。
- API 密钥只保存在当前页面内存，通过 `X-DeepSeek-API-Key` 请求头传给后端；不得写入源码、数据库、日志、浏览器持久存储或构建产物。
- 不配置 hash 验证。重复线索使用规范化来源链接等明确字段判断。
- 自动准入只表示允许自动归类或进入候选队列，不自动对外发布。
- 自动测试使用 `httpx.MockTransport` 或明确的本地 fake，不调用真实 DeepSeek 服务，不消耗真实额度。

## 功能与数据要求

热点线索至少包括：标题、内容摘录、来源平台、原文链接、发布时间、采集时间和可选互动数据。详情页展示当前类别、关注等级、分析结果及事件时间线。

分析结果至少包括：热点类别、摘要、关键词或相关实体、关注等级、置信度、原文证据、缺失信息、风险标记和建议动作。模型输出必须经过结构化校验；本地规则独立检查来源与时间完整性、时效性、重复来源、异常互动数据和需人工核验的风险信号。模型与规则不一致、字段不全或命中风险时，不得自动准入。

线索状态为 `pending`（待研判）、`tracking`（跟踪中）、`archived`（已归档）；分析状态为 `generated`（待复核）、`modified`（已修改）、`confirmed`（已确认）。人工确认后才把分析类别和关注等级应用到线索。所有状态变化与人工操作须写入审计事件。统计须区分已应用的类别和关注等级与尚未确认的分析建议。单次互动量不得被称为增长趋势；只有保存多个时间点的指标后才能计算增长。

API 应覆盖创建、服务端分页查询与筛选、详情、分析、人工修改、确认应用、状态更新、AI 连接测试和统计。前端不得继续只取前 100 条后在浏览器中筛选。请求中涉及分析、修改、确认和状态更新的操作必须检查线索版本；过期版本返回 HTTP `409`，客户端提示刷新后重试。

## 执行阶段与交付物

1. **基线检查**：阅读 `AGENTS.md`、本文件、`docs/architecture.md`（存在时）、相关源码与测试；检查工作区未提交改动及现有功能。输出包含文件所有权、API 契约、风险和验收标准的 implementation plan。
2. **数据分析**：定义字段、类别、时效与风险规则、去重口径、统计口径和演示数据矩阵。结果须交给实现及测试子智能体使用。
3. **后端实现**：建立热点线索、分析与事件数据结构；实现 API、规则、模型融合、事务、版本冲突和种子数据。模型网络请求期间不持有 SQLite 写事务。
4. **前端实现**：复用现有工作台布局，完成录入、服务端查询、详情、AI 分析、人工复核、确认、状态更新和统计；处理加载、空状态、上游错误及 `409` 冲突。
5. **独立测试**：将原 8 个测试函数的能力迁移到热点场景，并扩充边界与异常测试；在隔离环境运行后端测试和前端构建。测试子智能体只修改测试文件，发现实现缺陷应报告给对应实现子智能体修复。
6. **独立 review**：审查需求覆盖、接口兼容性、并发正确性、密钥处理、数据口径、错误处理和可维护性。按严重程度报告具体文件与行号；实现子智能体修复后再复核。
7. **主 Agent 验收**：核对所有必需用例、测试输出、构建结果和改动清单；更新 README，说明启动、配置、API、演示数据、状态流转与测试方式。只有验收项有证据支持时才能宣告完成。
8. **PR 创建与提交**：PR 责任人只在独立仓库功能分支上操作，确认测试、构建、本地部署测试和独立 review 证据后创建 PR；PR 描述必须列出实际命令、验收结果、风险与限制。review 反馈由该责任人形成补提交并更新 PR，不能以 fork 原仓库代替独立仓库交付。

## 测试验收矩阵

保留原有 8 类覆盖：本地规则高置信度分支、低置信度分支、DeepSeek 请求与结构化解析、上游安全错误、创建到统计的完整 API 流程、输入校验与缺失资源、缺少 API 密钥、密钥转发且不落库。

新增测试至少覆盖：重复链接；来源或发布时间缺失、过期与未来时间；负数或非法互动数据；模型非法 JSON、缺字段或枚举越界；超时、限流和上游不可用；模型与规则冲突；自动准入边界；重复确认；并发版本冲突 `409`；模型请求期间线索变化后的过期结果拒绝；数据库路径切换与空库演示数据；分页筛选及统计口径。测试不得把“测试文件存在”当作“测试通过”。

## 完成判定

后端测试通过、前端生产构建通过、主流程能从录入走到归档、默认数据库与 `TICKET_DB_PATH` 均可启动、密钥不落库、所有模型测试不访问真实上游，并且独立 review 的高优先级问题已修复，才可标记完成。最终报告列出实际执行的命令和结果、修改文件、未解决限制及其影响。
